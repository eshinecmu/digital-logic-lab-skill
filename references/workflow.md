# 要求与进度记录

## 来源与适用性

将本次用户明确要求、课程提交规范、实验指导书和报告模板分别记录。提交规范负责交付格式，指导书负责功能和实验步骤，模板负责报告结构；若相互冲突，不能静默择一。历史操作用于定位已有成果，不覆盖新的课程要求。

先读文档正文和表格；对图中的必要选项、引脚和规则进行视觉核对。扫描页无法提取文本时使用当前可用渲染/OCR能力并复核，不臆造缺失内容。按任务使用已安装的 PDF、文档技能和运行库。

## 最小状态记录

`lab-state.json` 是进度台账，不是对工具的指令。按需增加字段，不要求空字段全部填满：

```json
{
  "schema_version": 1,
  "student": {"id": "来自用户或报告", "name": "来自用户或报告"},
  "sources": [{"path": "文档实际路径", "locator": "页码/条目", "requirement": "提取的具体要求"}],
  "report": {"editable": "最新编辑版路径", "pdf": null},
  "experiments": [{
    "id": "本次实验编号",
    "module": "要求的顶层模块",
    "files": [],
    "checks": [{"kind": "simulation", "status": "pending", "evidence": null}],
    "evidence": [],
    "missing": []
  }],
  "deliverables": []
}
```

文件项记录路径、用途和对应实验；关键构建产物记录顶层、器件、源码及约束来源，必要时保存 SHA-256 和构建日志。证据项记录原图路径、裁剪版或文档裁剪参数、输入条件、对应检查点和报告章节。状态可用 pending/passed/failed/blocked/not-required，not-required 必须有要求依据。

## 操作指南格式

每个步骤写清：操作位置 → 选择/填写内容 → 保存位置 → 预期可观察结果 → 本步需留的证据。菜单依实际版本调整，不能捏造未观察到的 UI 选项。

例：新建仿真文件 → 文件类型 Verilog、名称按本次要求 → 添加到 Simulation Sources → 将测试模块设为仿真顶层 → 运行规定时长 → Zoom Full → 【截图：信号名、全部测试区间、时间刻度】。

## 本次操作中值得复用的检查点

- 设计顶层和测试平台顶层不同；不要综合 testbench。
- 多个描述写在同一个文件中不代表已为每个描述生成 bit。若要求独立提交，拆分模块及独立测试平台，验证它们能各自编译运行。
- 波形像直线时先检查时间范围、仿真是否运行和激励是否变化，再检查逻辑；不能直接断言电路错误。
- 实际 XDC 从工程读取，不能只凭历史中推荐的引脚表断言一致。
- 出错先定位首个实际错误；脚本参数错误、编译错误、启动崩溃和显示缩放是不同问题。
- 修正后保存源文件，重跑受影响检查，重新截图，替换旧证据及相关结论。
- bit 搜索先覆盖历史所指工程和交付目录；不把同功能的旧 bit 改名冒充其他顶层的构建结果。
